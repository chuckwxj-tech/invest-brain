SanDisk have HBF in development and soon testing.
Marvell have made announcements about their technology to help with the KV cache namely the CXL technology. 
Are these competitive or complementary?
-----------
Grok replies:

SanDisk HBF (High Bandwidth Flash)

What it is: A new memory tier that stacks specialized 3D NAND dies (with a logic base die, TSVs, and advanced packaging) in an HBM-like form factor. It uses UCIe for the host interface.
Key specs (first-generation / initial open OCP spec from Sandisk + SK hynix, August 2026): Up to 512 GB per stack (8-high or 16-high), read bandwidth grades from ~0.4 TB/s to 3.0 TB/s (first gen targeting ~1.6 TB/s), matching roughly HBM4 footprint/power/height. Future gens aim for higher capacity (1–1.5 TB) and bandwidth (>2–3.2 TB/s).
Status: First memory die taped out (announced at Sandisk’s August 2026 Investor Day). Memory samples targeted for 2H 2026 / product samples 2027; inference devices expected to sample in 2027, with broader commercial availability later (often projected 2028+). Open standard via OCP; Google and Tenstorrent are involved in the consortium.
Primary use case: High-capacity, high-bandwidth read-heavy storage of model weights (and similar relatively static data) placed very close to the accelerator (package-near). It is non-volatile (no refresh power) and far denser/cheaper per GB than HBM. Sandisk positions it as augmenting (not replacing) HBM—HBM keeps latency-sensitive working sets; HBF holds the bulk. Simulations claim near-parity with unlimited-HBM systems for weight reads on large models.

NAND’s high latency, lower write bandwidth, and limited endurance make pure drop-in use for highly dynamic, write-heavy data problematic.
Marvell CXL technology for KV cache

What it is: CXL (Compute Express Link) solutions—Structera family (memory-expansion controllers, near-memory accelerators, and switches for rack-level pooling), plus related SSD controllers and even photonic fabric ideas—for expanding and pooling memory.
Focus: Addressing the exploding KV cache (key-value cache) demands of long-context LLM inference. KV cache grows with context length and concurrent users; it is highly dynamic (frequent writes/updates as tokens are generated). Marvell enables offloading overflow KV cache to larger, shared CXL-attached DRAM (DDR4/DDR5 recycling is a near-term use case), with memory pooling across servers/racks, near-memory processing, and compression. Sub-microsecond access is targeted for “near-local” feel. Recent demos/announcements (including with SK hynix) show significant throughput gains for long-context models by keeping more KV cache accessible without forcing smaller batches or recomputation.
Status: More mature product family with shipping or sampling components; CXL switches and controllers already in the market or advancing rapidly in 2026 announcements.

CXL sits farther from the GPU (board- or rack-level) than on-package memory and relies on coherent load/store semantics over a PCIe-like physical layer.
Why complementary rather than competitive

Different data and access patterns:Model weights → mostly read-only or infrequently updated → excellent fit for HBF’s high-capacity, high-read-bandwidth, package-local NAND.
KV cache / activations → write-heavy, dynamic, needs lower latency and better endurance → better suited to HBM (hottest) + CXL-attached DRAM (warm overflow) + potentially SSDs (colder).

Different places in the hierarchy:HBF: Package-near tier (next to HBM on the accelerator package), aiming for HBM-class bandwidth at much higher capacity.
CXL: Board- to rack-scale expansion and pooling, adding shared capacity beyond what fits on the package.

Industry commentary and analyses treat them as parallel approaches to the same “memory wall” problem in inference (capacity constraints limiting batch size, context length, and GPU utilization). One analysis explicitly notes HBF as a package-near NAND capacity tier and CXL as extending memory farther away; both add capacity but in different physical locations and stages of maturity.

Systems can (and likely will) use both: HBM for hottest data + HBF for large static weights + CXL for pooled/shared dynamic KV cache overflow. Sandisk/SK hynix explicitly say HBF coexists with HBM; Marvell’s portfolio is multi-tier (HBM/local DRAM → CXL → optical shared → SSDs).
There is mild competitive pressure in the sense that both aim to reduce reliance on expensive HBM for capacity and improve inference economics (tokens per dollar/watt). If HBF becomes widely adopted for weights, it could free up HBM capacity that might otherwise be pressured by KV cache growth, indirectly helping (or changing the sizing of) CXL deployments. Conversely, very large CXL pools could reduce the urgency for on-package capacity solutions in some architectures. But the technologies themselves do not directly substitute for each other.
Bottom line: Complementary. HBF is a near-memory flash capacity play optimized for read-mostly model weights; Marvell’s CXL is a coherent expansion/pooling play optimized for dynamic KV-cache capacity. They address adjacent layers of the same AI inference memory problem and can coexist in the same systems.
